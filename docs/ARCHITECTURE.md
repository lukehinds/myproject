# Collaborative Whiteboard — Architecture & Contract

Status: authoritative. Set by the lead. Frontend and backend build against this
contract in parallel. If you need it changed, ask the lead — do not change it
unilaterally, and do not edit this file.

## 1. Product scope (MVP)

An Excalidraw-inspired whiteboard: draw shapes on an infinite canvas, several
people in the same room see each other's edits and cursors live.

Must have:
- Infinite canvas: pan, zoom, scroll-to-zoom, zoom controls, reset view.
- Tools: selection, hand (pan), rectangle, diamond, ellipse, arrow, line,
  freedraw, text, eraser.
- Per-element style: stroke colour, background colour, fill style, stroke
  width, stroke style (solid/dashed/dotted), opacity, roughness, font size.
- Manipulation: select (click + rubber-band), multi-select, move, resize via
  8 handles, delete, duplicate, z-order (front/back), copy/paste.
- Undo / redo (local history).
- Persistence: scene autosaves to the server; reload restores it.
- Collaboration: join a room by URL, see remote edits and remote cursors with
  names and colours, see who is present.
- Export: PNG and SVG of the scene, plus `.json` scene file save/load.

Explicitly out of scope for the MVP: images/embeds, libraries of shapes,
element grouping, binding arrows to shapes, end-to-end encryption, auth,
mobile-specific UI, laser pointer, frames.

## 3. Shared data model

All ids are strings (nanoid, 21 chars). All coordinates are in **scene space**
(infinite plane, y grows downward), never screen space.

```ts
type ElementType =
  | "rectangle" | "diamond" | "ellipse"
  | "arrow" | "line" | "freedraw" | "text";

interface Element {
  id: string;
  type: ElementType;
  x: number;              // top-left of bounding box, scene space
  y: number;
  width: number;          // may be negative before normalisation
  height: number;
  angle: number;          // radians, rotation about the bbox centre

  strokeColor: string;    // "#1e1e1e"
  backgroundColor: string;// "transparent" or hex
  fillStyle: "solid" | "hachure" | "cross-hatch";
  strokeWidth: number;    // 1 | 2 | 4
  strokeStyle: "solid" | "dashed" | "dotted";
  roughness: number;      // 0 | 1 | 2
  opacity: number;        // 0..100

  seed: number;           // stable rough.js seed, set once at creation

  zIndex: number;         // stacking order; float, so a element can always be
                          // inserted between two others. See §5 "Ordering".

  // linear elements ("arrow" | "line" | "freedraw") only
  points?: [number, number][]; // relative to (x, y); first point is [0,0]

  // text only
  text?: string;
  fontSize?: number;      // 16 | 20 | 28
  fontFamily?: "hand" | "normal" | "code";
  textAlign?: "left" | "center" | "right";

  // reconciliation (see §5)
  version: number;        // increments on every local mutation
  versionNonce: number;   // random uint32, re-rolled on every mutation
  updated: number;        // epoch ms, informational only
  isDeleted: boolean;     // soft delete — tombstones are kept and synced
}

interface AppStateSnapshot {
  viewBackgroundColor: string;
}

interface Scene {
  elements: Element[];          // includes tombstones
  appState: AppStateSnapshot;
}
```

Soft delete is required: deleting an element sets `isDeleted = true` and bumps
`version`/`versionNonce`. Hard-removing it would let a stale peer resurrect it.

## 4. Server API

Base URL: the server listens on `0.0.0.0:8000`. The Vite dev server proxies
`/api` and `/ws` to it, so the browser always uses same-origin relative paths.

### REST

| Method | Path                       | Body / Query          | Response |
| ------ | -------------------------- | --------------------- | -------- |
| GET    | `/api/health`              | —                     | `{"status":"ok"}` |
| POST   | `/api/rooms`               | —                     | `{"roomId": "..."}` — creates an empty room |
| GET    | `/api/rooms/{roomId}`      | —                     | `{"roomId","scene":Scene,"users":[Peer]}`; 404 if unknown |
| PUT    | `/api/rooms/{roomId}/scene`| `Scene`               | `{"ok":true,"scene":Scene}` — full snapshot merge, same rules as §5 |

### WebSocket

`GET /ws/rooms/{roomId}?name=<display name>` — upgrades to a WebSocket. The
room is created on first connect if it does not exist. Every frame is one JSON
object with a `type` field.

Server → client:

```jsonc
// first frame after connect, always
{"type":"init","userId":"...","roomId":"...","scene":{...},"users":[Peer]}
// another client changed elements (never echoed to the sender)
{"type":"elements","elements":[Element, ...]}
// presence: full list, sent whenever someone joins or leaves
{"type":"presence","users":[Peer]}
// another client's pointer moved
{"type":"pointer","userId":"...","x":12.5,"y":-3,"selectedIds":["..."]}
// the sender sent something invalid; the connection stays open
{"type":"error","message":"..."}
```

Client → server:

```jsonc
// elements the client created, changed or tombstoned — send only what changed
{"type":"elements","elements":[Element, ...]}
// local pointer in scene coordinates; throttle to <= 30/s, do not persist
{"type":"pointer","x":12.5,"y":-3,"selectedIds":["..."]}
// keepalive; server replies {"type":"pong"}
{"type":"ping"}
```

```ts
interface Peer {
  userId: string;
  name: string;   // from ?name=, else "Anonymous"
  color: string;  // assigned by the server from a fixed palette, stable per connection
}
```

Rules:
- The server is the authority on room state. It merges incoming elements with
  §5, stores the merged scene, and broadcasts **only the elements that actually
  won the merge**, to every client in the room except the sender.
- Unknown `type` values are ignored with an `error` frame, never a disconnect.
- A malformed element (missing `id`/`version`/`versionNonce`, wrong types) is
  rejected for that element only; valid siblings in the same frame still apply.
- Pointer frames are relayed, never stored.

## 5. Reconciliation (both sides implement this identically)

For an incoming element `b` against a local/stored element `a` with the same
`id`, `b` wins when:

1. `a` does not exist, or
2. `b.version > a.version`, or
3. `b.version === a.version && b.versionNonce < a.versionNonce`, or
4. `b.version === a.version && b.versionNonce === a.versionNonce &&
   canonical(b) < canonical(a)` (lexicographic byte comparison).

Otherwise `a` is kept.

`canonical(e)` is `e` serialised as JSON with its keys sorted, `updated`
omitted, and no insignificant whitespace — i.e. `json.dumps(e, sort_keys=True,
separators=(",", ":"))` and the JS equivalent. `updated` is excluded because §3
calls it informational; including it would make the tie-break depend on a
clock.

**Rule 4 is required, not optional.** `versionNonce` is a random uint32, so a
collision at the same `version` happens by chance and is trivial to force
deliberately. Without rule 4 the winner of such a clash depends on the order
the candidates happen to arrive in, and two clients fed the same edits in a
different order end up with different scenes — permanently, with no event to
signal the divergence. With rule 4 the merge is a total order on
(`version`, `versionNonce` descending, `canonical`), so it is deterministic,
order-independent and associative: any peer, given any permutation of the same
edits, converges on the same scene.

Implementations must also **collapse repeated ids within a single batch**: if
one frame carries v2 and v3 of the same id, apply the merge pairwise and
return/broadcast only the final winner for that id, never the intermediate.

### Ordering

Render order is **`zIndex` ascending, ties broken by `id` ascending** — higher
`zIndex` is on top. It is *not* array order. Array position carries no meaning
and peers must not rely on it.

`zIndex` is ordinary element data: it merges under the rules above like any
other field, so a z-order change is a normal mutation — set a new `zIndex` and
bump `version`/`versionNonce`, and peers reorder.

- Bring to front: `zIndex = max(all zIndex) + 1`.
- Send to back: `zIndex = min(all zIndex) - 1`.
- Insert between neighbours `a` and `b`: `zIndex = (a.zIndex + b.zIndex) / 2`.
  `zIndex` is a float precisely so this always has an answer.
- New elements are created at `max(all zIndex) + 1`.

On merge the server still keeps a winning element at the array position it
replaced and appends brand-new ids, but that is an implementation detail of
storage only. Both sides sort by `zIndex` at render time.

> Why this replaces the previous rule: the contract used to say z-order synced
> by moving the element within the array and bumping its version. That cannot
> work. The merge is per-element and keyed by `id` — it preserves the stored
> position of whatever it replaces and has no way to express "this element
> moved past that one", so a reordered array sent by one client is discarded on
> arrival and peers never reorder. Ordering has to live *in* the element to
> survive a per-element merge.

Every local mutation must bump `version` by 1 and re-roll `versionNonce`.
Never mutate an element received from the server without bumping both.

## 6. Persistence

Rooms persist to disk as JSON under `server/data/rooms/{roomId}.json`
(configurable via `WHITEBOARD_DATA_DIR`). Write is debounced (~1s) and atomic
(write to a temp file in the same directory, then `os.replace`). Rooms load
lazily from disk on first access, so a server restart preserves scenes. No
database.

Writes to a single room must be **serialised, and a write that has begun must
never be cancelled**. Debouncing happens *before* a write starts, not during
one. Cancelling an in-flight write does not stop the thread already performing
it, so a cancelled older write can land after a newer one and silently replace
the current scene with a stale one. Use a single writer per room (or a
generation counter that makes a late write a no-op). On shutdown, await the
in-flight write as well as the final save.

## 8. Quality bar

- Backend: pytest covering reconciliation, the REST endpoints and a two-client
  WebSocket round trip. `ruff check` and `ruff format` clean.
- Frontend: TypeScript strict, no `any` in exported signatures. `tsc --noEmit`
  and `eslint` clean. Vitest covering reconciliation, geometry (hit-testing,
  resize) and scene serialisation.
- Both: the reconciliation tests must cover the four §5 cases plus the
  tombstone-resurrection case, and must include a **permutation test** —
  feed the same set of conflicting edits in several different orders and
  assert the resulting scene is identical every time. That test is what
  actually proves §5, and it is the one that catches a broken tie-break.
- Both: a test that a batch carrying two versions of one id yields only the
  final winner.
- Backend: a test that a slow or non-reading peer cannot stall delivery to
  healthy peers, and a test that an interrupted/superseded save never leaves
  stale data on disk.
